## Overview

The Steel CLI lets you run full browser workflows from the terminal, end-to-end.
You can start a browser session, navigate pages, click/fill/type, extract content, and
stop the session without wiring custom browser infrastructure.

What it enables:

- Run browser automation in cloud mode (default) or self-hosted/local mode
- Drive pages with terminal-first browser commands (`navigate`, `snapshot`, `fill`, `click`, etc.)
- Use API tools for `scrape`, `screenshot`, and `pdf`
- Bootstrap projects with `forge`

In v0.5.0, browser actions use the HTTP Commands API. The browser engine runs
inside the Steel session; the CLI does not require a local browser daemon or
an `agent-browser` installation.

- GitHub: [steel-dev/cli](https://github.com/steel-dev/cli)

## Installation

Install with the official script (recommended):

```bash Terminal
curl -fsS https://setup.steel.dev | sh
```

This installs the stable native `steel` binary to `~/.steel/bin` and, in an
interactive terminal, runs `steel init`. Restart your shell or run
`export PATH="$HOME/.steel/bin:$PATH"` before using `steel` by name.

### Setup with your coding agent

Paste this into OpenCode, Codex, Pi, or Claude Code:

```text Prompt
Read https://setup.steel.dev/install.md and follow it to set up Steel for this coding client. Then continue my requested task using the installed Steel skill.
```

The guide installs the stable binary without interactive setup, then initializes
the selected client explicitly. For example, in Codex:

```bash Terminal
curl -fsSL https://setup.steel.dev/install.sh | sh -s -- --non-interactive
"$HOME/.steel/bin/steel" --version
"$HOME/.steel/bin/steel" --json init --agent --from codex
```

Use the matching `--from` value: `opencode`, `codex`, `pi`, or `claude-code`.
When approval is pending, the agent shows you the device authorization URL.
Approve it in your browser, then have the agent rerun the same init command.
Successful initialization installs the skill; the agent must still load it
through its native skill mechanism and verify the requested task.

- A Steel account is enough for device login; copying an API key is not required.
- Node.js/npm, including `npx`, is required when installing skills.
- Pass `--from` directly to `steel init --agent`. The installer's
  `STEEL_ONBOARDING_FROM` value is telemetry metadata, not a setup target.

## Quick Start

### Cloud Mode (Default)

```bash Terminal -wc
steel login
steel browser start --session my-job
steel browser navigate https://example.com --session my-job
steel browser snapshot -i --session my-job
steel browser stop --session my-job
```

### Self-Hosted Endpoint

```bash Terminal
steel browser start --api-url https://steel.your-domain.dev/v1 --session my-job
steel browser navigate https://example.com --api-url https://steel.your-domain.dev/v1 --session my-job
```

### Local Runtime (`localhost`) Flow

```bash Terminal
steel dev install
steel dev start
steel browser start --local --session local-job
steel browser navigate https://example.com --local --session local-job
steel browser stop --session local-job
steel dev stop
```

The self-hosted browser service must enable `ENABLE_COMMANDS_API=true` for these
actions. `steel dev start` does not enable that server setting automatically.
Cloud device credentials are not forwarded to a different API origin.

### Typical Agent Skill Workflow

Most agent loops follow this pattern:

1. Start or attach a named session.
2. Open a page and inspect interactable elements (`snapshot -i`).
3. Perform actions (`fill`, `select`, `check`, `click`).
4. Wait for the post-action state and verify output.
5. Stop the session when done.

```bash Terminal
SESSION="signup-demo-$(date +%s)"
steel browser start --session "$SESSION"
steel browser navigate https://example.com/signup --session "$SESSION"
steel browser snapshot -i --session "$SESSION"
steel browser fill @e1 "Jane Doe" --session "$SESSION"
steel browser fill @e2 "jane@example.com" --session "$SESSION"
steel browser select @e3 "California" --session "$SESSION"
steel browser check @e4 --session "$SESSION"
steel browser click @e5 --session "$SESSION"
steel browser wait --load-state networkidle --session "$SESSION"
steel browser stop --session "$SESSION"
```

References such as `@e1` come from the latest snapshot; replace the illustrative
refs above with the ones returned for your page. Use the Steel command help
rather than assuming every `agent-browser` option is supported.

## Command Model

### Steel-Owned Browser Lifecycle Commands

- `steel browser start`
- `steel browser stop`
- `steel browser sessions`
- `steel browser live`
- `steel browser captcha solve`

### Browser Actions (Commands API)

The CLI sends actions to the Commands API for the selected session. It does not
pass arbitrary commands through to a separate local browser runtime.

Common actions include:

- Page navigation: `navigate`, `back`, `forward`, `reload`
- Page understanding: `snapshot`, `snapshot -i`
- Interaction: `click`, `fill`, `type`, `select`, `check`, `press`, `hover`
- Data retrieval: `get text`, `get html`, `get title`, `get url`
- Synchronization: `wait`, `wait --load-state networkidle`, `wait --text`
- Debugging: `screenshot`, `status`, `cancel`

Use command help directly when needed:

```bash Terminal
steel browser --help
steel browser click --help
steel browser wait --help
```

## Common Workflows

### 1. Named Session Lifecycle

```bash Terminal
SESSION="job-$(date +%s)"
steel browser start --session "$SESSION"
steel browser navigate https://example.com --session "$SESSION"
steel browser snapshot -i --session "$SESSION"
steel browser get title --session "$SESSION"
steel browser stop --session "$SESSION"
```

### 2. CAPTCHA-Aware Sessions

```bash Terminal
# Manual solve mode
steel browser start --session my-job --solve-captcha
steel browser captcha solve --session my-job

# Auto solve mode (stealth preset)
steel browser start --session my-job --stealth
```

### 3. Download a File

After navigating to a report page, use its snapshot reference to click the
download link. Then retrieve the file before stopping the session:

```bash Terminal
# Replace @e3 with the download link ref from your session's snapshot.
steel browser click @e3 --session "$SESSION"
steel browser wait --download --output ./report.csv --session "$SESSION"
cat ./report.csv
steel browser stop --session "$SESSION"
```

Check the saved file and the requested result before reporting success. Use the
same named session throughout; cleanup should release only the session created
for your task.

### 4. API Tool Commands

```bash Terminal
# Scrape (markdown-first output by default)
steel scrape https://example.com

# Screenshot
steel screenshot https://example.com --full-page

# PDF
steel pdf https://example.com
```

## Endpoint Resolution

API endpoint selection follows one precedence chain:

1. `--api-url <url>`
2. `--local`: `browser.apiUrl` in `~/.config/steel/config.json`, or `http://localhost:3000/v1`
3. `STEEL_API_URL`
4. `https://api.steel.dev/v1`

For a session created elsewhere, use `--session <session-id>`. Stopping an
ID-attached session forgets its local attachment without releasing the cloud
session. Use an explicit `steel sessions release <session-id>` when release is
intended. There is no generic `--cdp` or `--auto-connect` passthrough.

## Auth, Config, and Updates

If you provision Steel through Stripe Projects, `stripe projects add steel/browser` writes a
standard `STEEL_API_KEY` that the Steel CLI can read from your environment. See
[Stripe Projects](/overview/stripe-projects).

```bash Terminal
steel login
steel config
steel logout
steel cache --clean
steel update
steel update --check
steel update --force
```

Disable auto-update checks (24-hour cache window):

```bash Terminal
steel scrape https://example.com --no-update-check
STEEL_CLI_SKIP_UPDATE_CHECK=true steel scrape https://example.com
CI=true steel scrape https://example.com
NODE_ENV=test steel scrape https://example.com
```

## Runtime and Output Notes

- Output is text by default, even when piped. Use `--json` for machine-readable
  output, including the full scrape API response.
- Displayed connection URLs redact sensitive query parameters.

## Troubleshooting

- `Missing browser auth...`: run `steel login` or set `STEEL_API_KEY`.
- `Failed to reach Steel session API ...`: confirm mode and endpoint settings (`--local`,
  `--api-url`, env vars).
- Session reuse issues: use a consistent `--session <name>` across every step.
- Local runtime issues: run `steel dev install` once, then `steel dev start`.
- Stale state: stop the specific named session you created, then start a fresh one.

### FAQ

:::faq
### How do I install the Steel CLI?

For agent-led setup, follow [setup.steel.dev/install.md](https://setup.steel.dev/install.md).
For a human terminal, run `curl -fsS https://setup.steel.dev | sh`, then restart
your shell or add `~/.steel/bin` to your current `PATH`.

### Can I scrape or screenshot a page from the terminal without writing code?

Yes. The CLI ships one-shot API tools: `steel scrape <url>` (markdown-first output
by default, `--json` for the full response), `steel screenshot <url> --full-page`,
and `steel pdf <url>`.
