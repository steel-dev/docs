Use an API key on your backend to create and manage Steel resources. To connect an agent to an existing browser, pass the session's returned `websocketUrl` directly to your browser framework. The URL includes a temporary JWT for that session, so the agent does not need your API key.

### Overview

Use the appropriate authentication method for each interface:

- **REST API**: as the `steel-api-key` HTTP header
- **SDKs (Node.js / Python)**: as a client option, or via the `STEEL_API_KEY` environment variable
- **Browser connections (CDP over WebSocket)**: use the returned `websocketUrl`, which includes a temporary session JWT in its `token` query parameter

An organization API key can access resources across your organization. A project API key is bound to its Steel project. Neither is limited to one browser session. Keep API keys in trusted server-side code and use a session JWT when delegating access to one browser.

### Getting Your API Key

1. Sign in at [app.steel.dev](https://app.steel.dev).
2. Open **Settings → API Keys** ([direct link](https://app.steel.dev/settings/api-keys)).
3. Click **Create API Key**, give it a descriptive name (for example `production`, `local-dev`, `ci`), and copy the value.

You can also provision a Steel project and `STEEL_API_KEY` from the Stripe CLI with
[`stripe projects add steel/browser`](/overview/stripe-projects).

:::callout
type: warn

### Save your key somewhere safe

The full key is only shown once at the moment of creation. If you lose it, you'll need to delete the key and create a new one.
:::

### Setting Up Environment Variables

Both SDKs and most example code in these docs assume your key is available as the `STEEL_API_KEY` environment variable. The easiest setup is a `.env` file in your project root:

```bash .env -wcn
STEEL_API_KEY=ste-your-api-key-here
```

Make sure `.env` is listed in your `.gitignore` so the key never lands in version control.

### Using the API Key

#### SDKs

If `STEEL_API_KEY` is set in your environment, the official SDKs will pick it up automatically. You don't need to pass anything explicitly.

<CodeTabs storage="languageSwitcher">

```typescript !! Typescript -wcn
import Steel from 'steel-sdk';

// Reads STEEL_API_KEY from the environment
const client = new Steel();

const session = await client.sessions.create();
```

```python !! Python -wcn
from steel import Steel

# Reads STEEL_API_KEY from the environment
client = Steel()

session = client.sessions.create()
```

</CodeTabs>

You can also pass the key explicitly, which is useful when you manage multiple keys or fetch the value from a secrets manager at runtime:

<CodeTabs storage="languageSwitcher">

```typescript !! Typescript -wcn
import Steel from "steel-sdk";

const client = new Steel({
  steelAPIKey: process.env.STEEL_API_KEY,
});
```

```python !! Python -wcn
import os
from steel import Steel

client = Steel(
    steel_api_key=os.environ["STEEL_API_KEY"],
)
```

</CodeTabs>

#### REST API

When calling the REST API directly, send your key in the `steel-api-key` header.

```bash cURL -wcn
curl https://api.steel.dev/v1/sessions \
  -H "steel-api-key: $STEEL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{}'
```

The same header works for every authenticated endpoint: sessions, files, credentials, profiles, extensions, and so on. See the [API Reference](/api-reference) for the full list.

#### Browser Connections (CDP over WebSocket)

Creating a session, or retrieving a running session, returns a `websocketUrl` containing a temporary session JWT. Use the complete URL as returned. Do not append `apiKey` or rebuild the URL from a session ID.

<CodeTabs storage="languageSwitcher">

```typescript !! Typescript -wcn
import { chromium } from "playwright";
import Steel from "steel-sdk";

const client = new Steel(); // Reads STEEL_API_KEY on your backend
const session = await client.sessions.create();
let browser;

try {
  browser = await chromium.connectOverCDP(session.websocketUrl);
  const context = browser.contexts()[0];
  const page = context.pages()[0] ?? (await context.newPage());
  await page.goto("https://example.com");
} finally {
  try {
    await browser?.close();
  } finally {
    await client.sessions.release(session.id);
  }
}
```

```python !! Python -wcn
from playwright.sync_api import sync_playwright
from steel import Steel

client = Steel()  # Reads STEEL_API_KEY on your backend
session = client.sessions.create()

try:
    with sync_playwright() as playwright:
        browser = playwright.chromium.connect_over_cdp(session.websocket_url)
        try:
            context = browser.contexts[0]
            page = context.pages[0] if context.pages else context.new_page()
            page.goto("https://example.com")
        finally:
            browser.close()
finally:
    client.sessions.release(session.id)
```

</CodeTabs>

Python exposes the same response field as `session.websocket_url`. Puppeteer accepts the URL as `browserWSEndpoint`; [Playwright MCP](https://github.com/microsoft/playwright-mcp#configuration) accepts it through `--cdp-endpoint`. See the [Playwright](/integrations/playwright), [Puppeteer](/integrations/puppeteer), and [MCP](/cookbook/mcp) examples.

Retrieve the individual running session before connecting if you found it through the list endpoint. Session list responses do not mint connect tokens. The live-details endpoint also returns a tokenized connection URL in `wsUrl`.

#### Temporary Session JWTs

The JWT contains the organization ID, session ID, and `session:connect` scope. Steel verifies its signature, issuer, audience, expiry, and the requested session. Replacing `sessionId` in the URL does not grant access to another browser.

- **Lifetime:** The token expires with the session's remaining configured lifetime. Retrieving the session again can issue a new token, but does not extend the browser's lifetime.
- **Availability:** Tokens are issued only for running sessions with time remaining. An ended session cannot be reconnected by requesting another token.
- **Access:** The token grants access to that browser session. It is not an API key for listing or managing your organization's profiles, credentials, or other sessions.
- **Browser authority:** The token is scoped to a session, not a website, tab, user, or individual action. Anyone holding it can use the authenticated browser state available in that session.

Treat the full WebSocket URL as a bearer credential. Share it only with the agent or user authorized to control that session, and keep it out of logs and public responses. Release the session from your backend when access should end. The JWT is signed independently of the API key, so API-key rotation is not a session-token revocation mechanism.

If a live-session response has no `token` parameter, token issuance may have failed. Retrieve the live session again or contact support. A backend delegating browser access should fail the handoff rather than append its API key as a fallback.

#### Delegating Browser Access to an Agent

1. Your backend authenticates the caller and checks your application's workspace/project permissions.
2. It selects the authorized [credential namespace](/overview/credentials-api/overview#namespaces) and, optionally, a [profile](/overview/profiles-api/overview).
3. It creates or retrieves the running session using its API key.
4. It returns only the tokenized `websocketUrl` to the authorized agent, which connects directly over CDP.
5. Your backend manages session release and any later requests for browser access.

Steel does not infer your application's membership rules from namespace names. Enforce those rules before choosing credentials, a profile, or a live session.

#### API-Key Connections

Direct CDP connections using `apiKey` remain supported for trusted server-side clients. Prefer the returned `websocketUrl` for an existing session. Adding `sessionId` to an API-key URL chooses a browser but does not restrict the key's permissions. Do not use an API-key URL as a session-scoped secret.

#### Steel CLI

The [Steel CLI](/overview/steel-cli) authenticates with the same keys. The easiest way is:

```bash Terminal -wcn
steel login
```

This walks you through signing in and stores a key locally. Alternatively, set `STEEL_API_KEY` in your environment and the CLI will use it directly: useful for CI and non-interactive environments.

### Managing Your API Keys

All key management happens in the [API Keys dashboard](https://app.steel.dev/settings/api-keys). From there you can:

- **Create** a new key: pick a clear name so you can later identify where it's being used.
- **View** the list of existing keys, when they were created, and when they were last used.
- **Delete** a key: this immediately revokes it. Any service still using that key will start receiving `401 Unauthorized` responses.

Steel does not currently expose key management through the public API: keys are only created and deleted through the dashboard.

#### Rotating Keys

To rotate a key without downtime:

1. Create a new API key in the dashboard.
2. Roll the new key out to all the places that use it (environment variables, secret managers, CI, etc.).
3. Verify traffic is flowing under the new key (the "Last used" timestamp in the dashboard will update).
4. Delete the old key.

We recommend using separate keys per environment (for example `production`, `staging`, `local-dev`) so you can rotate them independently and narrow the blast radius of a leak.

### Security Best Practices

- **Never commit keys to source control.** Use `.env` files (and `.gitignore` them), your platform's secret manager, or CI secrets.
- **Never ship keys in client-side code.** Steel keys are meant for trusted server-side environments. Exposing one in a browser bundle, mobile app, or public repo effectively makes it public.
- **Scope keys per environment.** One key per environment (prod, staging, dev) makes incidents easier to contain.
- **Rotate on suspicion.** If a key might have been exposed (in logs, a screenshare, a repo, a CI job), delete it and create a new one immediately.
- **Use the `name` field.** Naming your keys when you create them makes it much easier to audit and revoke the right one later.

### Troubleshooting

If Steel rejects your request, you'll get an HTTP `401 Unauthorized` with a short message explaining why:

- **`Invalid Steel API Key`**: the key you sent doesn't match any active key on your account. Double-check it for typos, trailing whitespace, or the wrong environment variable. If you recently deleted the key, it will no longer work.
- **`Missing API key`**: no `steel-api-key` header was sent. Make sure your SDK client was initialized with a key, or that the header is present on your raw HTTP request.
- **`Account suspended`** (`403 Forbidden`): your organization has been blocked. Reach out to [team@steel.dev](mailto:team@steel.dev?subject=Account%20Suspension) to resolve this.

A quick way to sanity-check a key is to hit the sessions endpoint:

```bash Terminal -wcn
curl -i https://api.steel.dev/v1/sessions \
  -H "steel-api-key: $STEEL_API_KEY"
```

A `200 OK` means you're authenticated. A `401` means the key is wrong or missing.

### FAQ

:::faq
### How do I authenticate requests to the Steel API?

Use the `steel-api-key` HTTP header for REST requests, or the `STEEL_API_KEY` environment variable or client option for the SDKs. For CDP browser connections, use the session's returned `websocketUrl` directly. It includes a temporary JWT, so you do not need to append an API key.

### Can an agent connect without my Steel API key?

Yes. Have your backend authorize the request, create or retrieve a running session, and return its tokenized `websocketUrl`. The agent can connect to that browser directly. The JWT is valid for that session's remaining lifetime and cannot be used to connect to a different session.

### Does a session JWT restrict the agent to one domain?

No. It grants browser access to one session, including the authenticated state loaded into it. Use a dedicated credential namespace and profile for the connected account, and enforce any domain or action restrictions separately.

### Where do I get a Steel API key?

Sign in at app.steel.dev, open Settings → API Keys, click Create API Key, and copy the value. The full key is shown only once at creation, so save it somewhere safe; if you lose it you must delete it and create a new one.

### Why am I getting a 401 Unauthorized from Steel?

A 401 means your key is invalid (typo, trailing whitespace, wrong env var, or recently deleted) or missing (`Missing API key` means no `steel-api-key` header was sent). A quick sanity check is `curl -i https://api.steel.dev/v1/sessions` with your key header: 200 means authenticated.
:::
